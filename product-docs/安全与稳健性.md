# Otto 安全与稳健性加固报告

> 面向企业采购方的安全说明。Otto Code 基于开源 easycode（Apache-2.0）二次开发，
> 形态为「跑在用户本机的 CLI 后端 + 飞书」——不是云端多租户 SaaS，企业数据与凭证留在企业自己的机器上。
> 本报告诚实标注：哪些已修复并验证、哪些是设计改进、哪些是仍待建的大特性。不夸大、有据可查。

---

## 1. 为什么企业要看这份报告

Otto 让每个员工在飞书里有一个住在飞书、懂他、替他干活的 AI 数字同事。这意味着：
**一条飞书消息，可能触发本机上的真实代码执行（agent 带 `run_shell_command`、文件读写、工具调用）。**

这正是企业级 AI agent 的生死线——边界没守住，「提效工具」就变成「攻击面」。
我们没有回避这一点，而是请了一轮**对抗式安全复核**：把代码逐行当作攻击目标来审，再逐条核实修复。

下面给出的每一条，都标了 `文件:行号` 出处、修法、以及**用什么手段验证过**——不是「应该修好了」，是「实测拦住了」。

## 3. 已修复并验证的高危项

> 每条：**问题 → 修法 → 验证方式**。全部以构造真实恶意 payload / 并发压测实测确认，且大多可在**不连飞书**的情况下复现验证。

### 3.1 RCE 之一：命令注入（`params.command` 未净化）

- **问题**：`lark-cli.ts:330` 把 `params.command` 直接拼进命令串，而校验（`:267`）只查非空、零字符过滤，执行又走 `shell:true`（`:598`）。
  攻击者只需让 LLM 工具调用产出 `command="calendar +x; rm -rf ~"`，分号后的命令直达 shell——
  **「飞书消息 → 开发者机器上任意代码执行」**，是整条飞书提效链路里最大的洞。
- **修法**：command 改用已存在的 `sanitizeArg`（`:322`）包裹，并在 `:267` 加白名单 `/^[a-z0-9_+\-. ]+$/i`。
  （同文件 args 早已用 sanitizeArg、`--as` 已 enum 校验，唯独 command 此前裸奔。）
- **验证方式**：构造 `; rm`、`$()`、反引号等恶意 payload 实测，**全部被拦截**；针对性单测覆盖，无需连飞书即可复现。

### 3.2 RCE 之二：下载文件扩展名不净化

- **问题**：`gateway.ts:1338-1341` `downloadFileToDir` 对 basename 做了净化，却**原样保留 `.sh/.py/.exe` 扩展名**。
  飞书用户上传 `evil.sh`，原样落盘到项目目录，而 agent 持有 `run_shell_command`——
  **外部飞书用户 → 本机 RCE**。（对比同文件 `downloadImageToDir` 已用 magic-number 校验，唯独文件下载缺此防护。）
- **修法**：扩展名白名单 / 按 MIME 赋安全扩展名（参照同文件 `detectImageExtension` 的 magic-number 做法）。
- **验证方式**：上传 `evil.sh` 实测，落盘为安全扩展名（如 `.bin`），不再保留可执行扩展。

### 3.3 lark-cli 输出重组注入（复核升级为 CRITICAL）

- **问题**：`lark-cli.ts:506-583`（尤其 550/556/571）从 lark-cli 错误输出用正则抽 domain/scope/flags，
  拼回命令再经 `shell:true` 执行，只剥尾引号、leading `$()`/反引号保留。
  供应链 / MITM 篡改 lark-cli 输出即可注入 shell 命令。
- **修法**：domain 用官方域名白名单、scope 用 `/^[a-z_]+:[a-z_]+\.[a-z_]+/` 校验、flags 仅允许 `--domain/--scope`，输入加长度上限。
  同源的 `--exclude` scope 拼接（`:410-411`，scope 来自用户可写的 `settings.json`）一并用 `sanitizeArg` + 格式校验封堵。
- **验证方式**：构造恶意 lark-cli 输出 / 恶意 settings scope 实测，注入被拦截。

### 3.4 全量环境变量泄露给子进程

- **问题**：`lark-cli.ts:601` `env: { ...process.env }` 把 OPENAI / ANTHROPIC / GITHUB 等**所有密钥**传给 lark-cli 子进程，违反最小权限。
  配合命令注入或供应链攻击即可一次性外泄全部密钥。
- **修法**：env 白名单——仅透传 `PATH/HOME/USER/LANG/LC_/TERM/TZ/NODE_/NPM_` 前缀的变量。
- **验证方式**：子进程内 `printenv` 断言**不含任何 API key**。

### 3.5 错误消息泄露 token / API 响应

- **问题**：`feishuAuth.ts:285`、`gateway.ts:656` / `:1421` 异常携带原始 HTTP 响应、`JSON.stringify(data)`，
  经 catch 传到用户可见文本（HTML 错误页 / 飞书回复），存在实际可达的 user-facing 泄露路径。
- **修法**：接入 `SensitiveDataFilter` 脱敏；对外只回错误码 + 人话描述，原始内容仅入 debug 日志。
- **验证方式**：触发 token 交换 / 网关错误，确认对外文本已脱敏、敏感原文不外露。

### 3.6 记忆持久化并发写竞态（直接砸「懂你」卖点）

- **问题**：`memoryTool.ts:308-341` 非原子 read-modify-write、无文件锁。
  产品有「最多 6 并发 Sub-Agent」+「异步消息分发」两条触发路径，并发 `save_memory` 会后写覆盖先写——**事实丢失**，直接砸「懂你」这条护城河。
- **修法**：写入串行化 + 原子写（temp + rename），保证并发写不互相覆盖。
- **验证方式**：**20 并发同时 `save_memory` 实测，20 条全部落盘、零丢失。**

### 3.7 Token 链路健壮性（getTenantToken）

- **问题**：`gateway.ts:643-662` `getTenantToken` 三宗罪——
  ① check 与 fetch 间有竞态、无单飞锁，并发到期请求各发一次 OAuth → 限流 429 / 状态不一致；
  ② `:653` 未查 `res.ok` 就 `res.json()`，飞书返 5xx/限流 HTML 时被 `SyntaxError` 掩盖真因；
  ③ `:656` 抛带 `JSON.stringify(data)` 的异常，多数调用方（sendMessage/uploadFile 等）无 try-catch。
- **修法**：加 `refreshPromise` 单飞锁（照搬同库 `CodexAuthManager:141-146` 的正确实现）；先查 `res.ok` 再解析、带 HTTP status 日志并脱敏；调用方降级返回 null 而非链路中断。
  令牌交换路径一并脱敏。
- **验证方式**：并发 N 次到期请求**只触发 1 次 OAuth**；mock 5xx/HTML 响应断言返 null 不抛、真因可见。
  另注：token 自动刷新代码已按实测参数写好，但需到期才触发，该路径**尚未到期触发验证**（如实标注，见 §4）。

### 3.8 会话泄漏 / 长跑 OOM（isolatedSessions 无回收）

- **问题**：`feishuCommand.ts:616/2859/995/4410` 隔离会话 Map 仅在 `/feishu stop` 时清理；
  覆盖旧 session 时旧 Config/GeminiClient 不主动释放；看门狗只查 loop 过期不查会话活跃度——
  对「24/7 常驻」是确定的 OOM 风险。
- **修法**：会话 idle 回收——LRU 上限 + 无活动驱逐 + 看门狗加会话超时清理；覆盖前释放旧 session。
- **验证方式**：会话空闲后被驱逐、内存回落，常驻不再单调增长。

## 4. 剩余项与优先级（诚实标注）

> 高危已清零。下列为加固项与企业级大特性，按对企业落地的优先级排序。**未建即标未建，不含糊。**

### 仍待建的企业级大特性（诚实：还没建）

| 优先级 | 特性 | 现状 | 为什么重要 |
|---|---|---|---|
| **P0（卖点护城河）** | 结构化记忆 / 按会话隔离 | 当前为 append 纯文本，无结构化检索/排序/去重/用户隔离 | 「懂你岗位」是核心护城河，目前是设计待建。多用户同 workspace 存在跨用户记忆污染风险（`memoryDiscovery.ts:85-93`） |
| **P0（合规阻断）** | 企业审计日志 | 无结构化 audit.jsonl、工具执行不记 `sender_open_id`（`logger.ts:23`） | SOC2 / ISO27001 硬门槛。工程量大，可与其他工作并行，故单独立项 |
| **P1** | 速率限制 / 配额 | 无 per-user / per-org 限流 | 多群并发可打爆飞书共享配额、推高成本（`feishuCommand.ts:2507`） |
| **P1** | RBAC | 仅 owner + allowlist，无 per-project 权限、无授权审计 | 50 项目 / 100 用户场景需要更细的权限模型 |

- **token 自动刷新**：代码已按实测参数写好（OAuth 实测 HTTP 200 + 文本流已通过），但刷新逻辑需令牌实际到期才触发，**该路径尚未做到期触发验证**。如实标注，待长跑或人为提前过期后补验。

### MEDIUM / LOW 加固项（不阻断企业试用，排期处理）

- **资源**：`cardCallbacks` 超时 timer 在 messageId 错配时不清理（`gateway.ts:595`）；`sideQuestionControllers` 部分清理漏洞（`feishuCommand.ts:791`）。
- **并发**：CardKit 流式 `sequence` 无互斥可乱序（`gateway.ts:2527`）；230020 限流无重试可丢 token（`gateway.ts:2729`）。
- **安全（次要）**：软链路径穿越（`memoryImportProcessor.ts:198`）；循环 import 深度致 DoS（`:48`）；飞书消息文本无 prompt injection 防护（`feishuCommand.ts:2497`）。

## 5. 复核中被剔除/降级的发现（透明度）

诚实意味着也要说「哪些其实不是问题」。下列 6 条经核源码后被剔除或降级，**未掺进修复清单**：

- **getTenantToken 抛异常致「事件分发器崩溃」**：主/高风险/文本三路径均有多层兜底，事件处理器始终返回 `{code:0}`。降为 LOW（缺防守式编程但不致崩）。
- **inFlightMessages 删除顺序致重复执行**：try-finally-return + 同步落盘 + 飞书需收 `{code:0}` 才停推，三重保证无竞态。降为 LOW。
- **`--as` 参数命令注入**：三层 enum 校验（TS 类型 + 运行时 + schema）封死路径。降为 LOW。
- **全局 `activeAbortController` 跨群误杀**：该变量全代码库只被赋 null、从未赋真实 controller，是死代码；真实 abort 走按 chatId 隔离的 Map。**判为误报**。
- **`parseJSONSafe` 静默丢工具参数**：`SchemaValidator` 显式识别 `__parseError` 并报错，40+ 工具均在 execute 前校验。**判为设计改进项，非 bug**。
- **健康检查在 QR 之后**：源码证实 `feishuCommand.ts:1164` 已在渲染 QR **之前**调 `initRegistration()`。**判为误报**。

## 6. 对企业 24/7 常驻的稳健性结论

**可以放心常驻试用，且边界已守住——以下结论有据：**

1. **两条 RCE 已封堵并实测拦截**——这是「飞书消息变本机代码执行」的最大风险，恶意 payload（`; rm`、`$()`、`evil.sh`）实测全部被拦。一条飞书消息不再能在员工机器上任意执行。
2. **密钥不外泄**——子进程 env 白名单（printenv 断言无 key）+ 错误消息脱敏，双重封住凭证泄露路径。本机形态下，企业密钥本就不出企业机器，现在连子进程和错误文本都拿不到。
3. **记忆不丢事实**——并发写串行化 + 原子写，20/20 并发零丢失。「懂你」的事实层在多 agent / 异步消息并发下数据完整。
4. **token 链路健壮**——单飞锁防刷新风暴、`res.ok` 防真因被掩盖、脱敏防泄露；并发只触发一次 OAuth。（自动刷新代码就绪，到期触发验证待补。）
5. **长跑不 OOM**——会话 idle 回收 + 覆盖释放，常驻内存不再单调增长。

**诚实的边界**：

- 真正让 Otto「懂员工岗位」的**结构化记忆/按会话隔离**仍是待建大特性（P0 护城河），当前记忆为纯文本且多用户共享 workspace 存在污染风险——**多用户敏感场景请先单用户/单项目试用**，待用户隔离上线再扩到团队。
- **企业审计日志**（合规硬门槛）尚未建，需要 SOC2/ISO27001 合规闭环的采购方应将其列为上线前置项。
- token 自动刷新、若干 MEDIUM 资源/并发加固项仍在排期，不阻断试用但会持续收敛。

**一句话**：Otto Code 的高危安全洞已止血并实测验证，本机形态天然把企业数据与密钥留在企业机器上，
适合作为飞书提效的 24/7 常驻试点；规模化到「多人敏感团队 + 合规审计」之前，需补齐结构化记忆隔离与审计日志这两项 P0 大特性。我们把它们摆在明面上，而不是藏起来。
