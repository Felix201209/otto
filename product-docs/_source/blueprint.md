# 产品蓝图 ·「飞书里,人人有 agent」

> 代号「新品牌」｜基于开源 easycode(原 DeepV Code,Apache-2.0)二次开发的独立新产品

## 1. 一句话定位 + 电梯陈述

**一句话定位:**
> **飞书里,人人有 agent —— 扫码即得,懂你岗位,替你干活。**

**电梯陈述(30 秒版):**
> 今天企业 AI 是"公司搭一个 Agent 平台,全员共用一个机器人"。我们反着来:**每个员工扫码 30 秒,就拥有一个属于自己、记得自己、用自己飞书身份干活的数字同事**。它原生活在飞书里,能打理日历、文档、表格、邮件、云盘、任务、OKR、知识库——这些能力我们继承自一套已经打磨成熟的开源底座(18 个飞书业务域全打通)。它跑在 DeepSeek/GLM 等国产模型上,成本极低、数据可不出域。对标飞书官方 Aily 是"公司养的一个新同事(共享)",我们是"**你私人的一个新同事(专属、跟你走)**"。

**为什么是现在:** 飞书深度集成的工程纵深(消息网关、扫码建应用、全套 API 封装)已经由开源底座现成提供;国产模型把单座成本压到 ¥10/月以下;而 Aily 受其平台商业模式约束,结构上做不了"自下而上、人人一个、本人身份"——这是一个时间窗口。

## 2. 护城河:对标飞书 Aily 的差异化

### 2.1 战场定性:这是"终端产品 vs 工具平台"的代差错位

| 维度 | 飞书 Aily | 钉钉 AI 助理 | **我们(新品牌)** |
|---|---|---|---|
| 本质 | 企业级 Agent **搭建平台**(低代码) | 平台内置官方助理 | **终端产品**:人人一个数字同事 |
| 谁来配 | 企业 IT / 业务管理员搭好下发 | 平台 + 管理员 | **员工本人扫码即得,无需 IT** |
| 分发单位 | 一企业建若干 Bot,全员共享 | 平台级助理 | **1 员工 = 1 专属 agent** |
| 操作身份 | 产物归机器人(应用身份) | 归机器人 | **归员工本人**(user_access_token) |
| 个人化 | 弱(面向场景,非面向人) | 弱 | **以"懂这个人的岗位与历史"为核心** |
| 模型主权 | 锁飞书/字节生态 | 锁钉钉/阿里生态 | **可接 DeepSeek/GLM/Kimi,可私有部署** |

**核心判断:** Aily 和钉钉是"平台",平台的天职是"通用 + 可治理",这恰恰决定了它在"个人化、开箱即用、本人身份"上有**结构性软肋**——不是它没想到,是它的商业模式和组织形态让它不会优先做。**这就是我们的缝。** 我们不在平台层正面打,只打它结构上做不到的三处。

### 2.2 五条护城河(按可防守强度排序,诚实标注成色)

> 护城河 ≠ "我们有个功能",而是"对手即使看见也学不动 / 不愿学"。

**① 零配置分发:扫码即得专属 agent(强,但有依赖风险)**
员工扫码 → 飞书侧自动创建 PersonalAgent 应用 → 即刻拥有专属 agent。把"企业级 agent 落地"从"IT 项目"压缩成"个人 onboarding 动作"。
- **Aily 为什么学不动:** 不是技术难度,是**商业模式冲突**——Aily 的钱和治理逻辑建立在"企业统一搭建下发",做"绕过 IT 的个人自助"等于自拆 B 端打法。
- **⚠ 真实风险(必须正视):** 这个自动建应用走的是飞书 `accounts.feishu.cn/oauth/v1/app/registration` **未公开私有协议**,源码注释白纸黑字写"飞书可能任意更改/下线"(`registration.ts` L16)。**这是护城河,也是单点故障。** 对策见红线第 8 节。

**② 操作归本人身份(强,最难复刻、最值钱)**
一切"替员工干活"的业务操作(日历/文档/表格/云盘/任务/OKR/邮件)走 `user_access_token`(员工本人身份),而非 bot 身份。我创建的日历是"我"创建的,不是"某机器人"。
- **附带的安全红利(说服 IT 的核心卖点):** 走本人 token,**飞书原生权限体系自动成为第二道闸门**——员工本来看不到的文档,他的 agent 也看不到。比 bot 身份(tenant token 能越权访问全租户数据)安全得多。
- **底座已就绪:** `lark-cli --as user` 原语已存在(`lark-cli.ts:344`),缺的只是多用户 token 管理。

**③ 个人长期记忆 + 岗位画像(潜力最强,目前最虚,必须砸资源做实)**
agent 跨会话记住"这个人是谁、负责什么、偏好、历史决策、常打交道的人和文档",越用越懂。这是真正能锁客户三年的**数据飞轮**——用得越久迁移成本越高。
- **🚧 现状缺口(不粉饰):** 现在记忆只是把事实追加进项目根的 `DEEPV.md` 文件(`memoryTool.ts:256`),**没有结构化、没有检索、没有岗位画像、没有从飞书行为自动学习**。**这条护城河现在深度约等于 0**,"天生懂我"目前是营销话术多过技术现实。这是 R&D 第一优先级。

**④ 飞书全域深度集成的"既成事实"(中强,工程纵深)**
继承的 `lark-cli` 已覆盖 **18+ 飞书业务域**,且有 WS 长连接网关、OAuth 动态接管、消息去重/重连/限流等大量**真实踩坑后的工程细节**。一个从零做飞书 agent 的创业公司,光把这 18 个域都接稳就够喝一壶。
- **取舍:** 深耕飞书 = **放弃钉钉/企微**。飞书生态外的客户直接放弃,不浪费销售资源。

**⑤ 部署主权 + 模型中立(中强,打数据敏感客户)**
可私有部署、自带合规 API key、接国产模型。对金融/政企/制造给"私有部署 + DeepSeek/GLM 自带"方案——**这是 SaaS 平台 Aily 给不了的客户**。底座已支持"自定义模型(无需登录)",几乎零改造。

> **诚实定级:** 开源底座本身**不是护城河**(对手也能 fork 同一上游)。它的价值是**早期速度与成本结构**,不是长期壁垒。真正的壁垒是叠加在底座上的私有部分(护城河①②③)。对客户别讲"我们开源",客户不关心;当内部研发杠杆用。

## 5. 多租户技术架构

### 5.1 核心决策:不深 fork,而是把 easycode 降级为"单员工 worker",外套多租户控制平面

```
┌──────────── 控制平面 Control Plane(新写,租户无关全局服务)────────────┐
│  租户管理 · 员工目录 · OAuth身份编排 · 密钥库(KMS) · 计费 · 审计 · 后台   │
└──────────────────────────────┬─────────────────────────────────────────┘
                  内部 gRPC / 事件总线(Kafka/Redis Stream)
┌──────────────────────────────▼─────────────────────────────────────────┐
│  数据平面 Data Plane(每租户隔离 · 可弹性伸缩)                            │
│  Agent Runtime Pool(每实例 = 一个 easycode worker,绑一个租户)          │
│   ├ FeishuGateway 实例(复用 gateway.ts;去重状态外移 Redis)            │
│   │   · tenant_access_token 管消息/卡片/群                              │
│   ├ Per-Employee 执行单元                                                │
│   │   ├ Memory Svc(pgvector,namespace=<tenant>:<employee>)            │
│   │   ├ RBAC 闸门                                                        │
│   │   └ lark-cli 子进程(--as user,注入 HOME=<tenant>/<emp>/lark-home) │
│   └ Model Gateway(provider 抽象:DeepSeek/GLM/Kimi/本地,合规 key)      │
└──────────────────────────────┬─────────────────────────────────────────┘
                     飞书开放平台 API     国产大模型 API
```

**三层分离的理由:** 控制平面是全局单例(租户表/计费/密钥不随 worker 重启丢);数据平面租户隔离可伸缩(一个租户挂不影响别人);两者只通过受控接口通信,**让 SaaS 和私有化共用一套代码,只换部署拓扑**。

### 5.2 身份隔离的技术抠点(最小改动、最高性价比)

`lark-cli` 是子进程,token 存它自己的 HOME。**把 `lark-cli.ts:601` 写死的 `env: {...process.env}` 改成由当前员工上下文注入 HOME + 租户凭证**,即可进程级隔离每个员工的 `user_access_token`,互不串号。
- **为什么靠 lark-cli 的本地 HOME 而非中心自建 OAuth:** lark-cli 已把"device-flow + refresh 续期 + 18 域 API 封装"全做好(854 行)。重写一套中心 OAuth + 全 API 封装是几个月的活且要永远追飞书 API 变更。让 lark-cli 当"每员工身份执行器"、中心只管编排和加密备份 refresh_token——**取舍可逆**,后续要强管控再收口。

### 5.3 权限双闸门

```
员工指令 → 闸门一(我们的 RBAC:角色 + 工具级开关)
        → 闸门二(飞书原生:用本人 token,飞书自动校验"他能不能看这张表")
        → 执行 + 审计留痕
```

### 5.4 技术选型汇总

| 层 | 选型 | 理由 |
|---|---|---|
| Agent Runtime | 复用 easycode(降级为 per-tenant worker) | 飞书能力现成,不重造 |
| 身份执行器 | lark-cli 子进程 + 注入 HOME 隔离 | 复用 device-flow + 18 域,改动最小 |
| 控制平面 | **混合:worker 用 TS(同栈),控制平面用 Go**(高并发网关) | 省心 + 并发强 |
| 主数据库 | Postgres + RLS(行级安全) | 多租户隔离成熟方案 |
| 向量记忆 | pgvector 起步 → Qdrant/Milvus 规模化 | 起步同库省运维 |
| Embedding | 国产合规(BGE / GLM-embedding) | 与模型层同合规口径,不出境 |
| 计费分析 | ClickHouse | 用量埋点海量,列存聚合快 |
| 状态/去重/路由 | Redis | WS worker 无状态化、去重外移、租户路由 |
| 密钥库 | Vault / 云 KMS(interface 抽象) | SaaS/私有化双形态可换实现 |
| 部署 | k8s + Helm(SaaS) / docker-compose(私有化小客户) | 同构交付,不分叉 |

> **架构红线:** 业务代码**绝不直接 import 具体 KMS/计费 SDK**——全走 interface,SaaS 注入云实现、私有化注入本地实现。这是两条交付线不分叉的前提,第一天就要解耦。

## 6. Agent 人设与 Onboarding

### 6.1 定调:它不是"AI 助手",是"你工位隔壁的新同事"

| 记忆 | 每次从零 | 记得岗位/项目/偏好 | `save_memory` + `DEEPV.md` |
| 主动性 | 纯被动 | 早会提醒、日报草稿 | scheduled-task + gateway |
| 边界感 | 有求必应 | "发邮件这种对外动作我先拟稿等你确认" | `--confirm-send` |
| 语气 | 客服式正确废话 | 干练同事,先结论、说人话 | system prompt 语气段 |

施工位:`prompts.ts` 加 `'colleague'` 人设档(与现有 codex/cursor 并列),动态填充 owner 岗位/姓名(锚点已在 1291 行飞书 channel context 注入块)。

**语气宪法 5 条(写进 prompt):** ① 先结论后展开,手机第一屏必须有用 ② 像同事不像客服(不用"非常抱歉给您带来不便")③ 不懂只问最关键一个,绝不杜撰事实 ④ 对外/不可逆动作永远先拟稿等确认 ⑤ 说人话、排版给手机(不输出超宽表格)。

### 6.2 Onboarding(★ 核心 UX 缺口,registration poll 成功后目前无任何引导)

poll 成功后立刻触发飞书交互卡片(代码已支持 card.action.trigger):
- **第 1 卡 · 认主:** "你好 XX!我是 [名字],从今天起做你的数字同事。我读了通讯录,你是「市场部」的「运营」,对吧?" → 点击写入 `save_memory` 第一条
- **第 2 卡 · 当场演一件真事(不列功能表):** "我先帮你看眼今天日程" → 真跑 `calendar +agenda` 渲染卡片 → "它真能读我日历" = 信任建立的关键一刻
- **第 3 卡 · 3 个高频入口 + 授权说明:** 引导"今天邮件有啥要紧的"等;说明"对外动作我永远先给你看草稿"
- **第 4 卡 · 主动性开关:** "要不要每天 9:00 给你今日速览?"(可关)→ 写入 scheduled-task

**6 个日常剧本技能卡(上层封装,用户感知的"开箱即用"):** 📅日程管家 / 📝会议闭环 / 📊数据搬运 / 📧邮件分诊 / ✅任务OKR / 📚知识库速查。底层全是 lark-cli 编排,首发只做这 6 个,高危/对外动作放二期。

## 7. 商业化:定价 + 成本 + 交付线

### 7.1 成本结构(国产模型,prompt caching 是生死线)

> **致命前提:** "agent 常驻飞书、重 context、重工具回灌"的负载,单任务 2 万–8 万 token。系统提示 + 工具 schema + 岗位记忆每次重复,**必须命中 prompt cache**——DeepSeek 缓存命中价是未命中的 **1/50**($0.0028 vs $0.14 /M)。caching 不是优化项,是毛利命门。

已查证真实单价(2026-06,DeepSeek 官方美元 / 智谱人民币):

| 模型 | 输入未命中 | 输入命中 | 输出 |
|---|---|---|---|
| **DeepSeek-V4-Flash(主力)** | $0.14/M | **$0.0028/M** | $0.28/M |
| DeepSeek-V4-Pro(规划类任务) | $0.435/M | $0.003625/M | $0.87/M |
| GLM-4.6(合规冗余/议价筹码) | ¥5/M 档 | — | — |

> ⚠ 合同写"V4-Flash",别写旧名 deepseek-chat(2026-07-24 弃用)。GLM **不是更便宜**($0.7/M 比 Flash 贵),它的角色是 failover + 信创清单可选项 + 对 DeepSeek 议价的备胎。

**单位经济(中度活跃员工建模:176 任务/月,5万 input + 5千 output/任务,70% 缓存命中):**
- 单座位月模型成本 ≈ **¥4.5** ｜ + 基础设施摊销 ¥3–5/座位 → **真实 COGS ≈ ¥8–10/月/座位**
- 失控警戒线:缓存命中跌到 30% → ¥13/座位。**两个护栏:** ① 缓存命中率监控,跌破 50% 报警 ② per-seat 月 token 软上限 + 超额降级(Pro→Flash),不断服。

> **⚠ 投资人会问的两个未验证假设(需 Pilot 实测校准):** ①单任务 5万 token、月 176 任务是建模拍的;②70% 缓存命中取决于工程上把系统提示/工具 schema/岗位记忆做成稳定可缓存前缀——**建议立刻验证 easycode 当前是否已对 DeepSeek 开 prompt caching**。

### 7.2 定价档(per-seat,核心卡位 = 用固定价打 Aily 的"token 计费不可预测焦虑")

| 档位 | 价格 | 对象 | 毛利 |
|---|---|---|---|
| **Free Pilot** | ¥0,限 1 部门 ≤30 人,60 天 | 冷启动钩子 | 获客成本 |
| **Team 标准版** | **¥39/座位/月**(年付 8.3 折) | 中小企业、单部门铺开 | COGS≈¥10 → **~74%** |
| **Business 进阶版** | **¥79/座位/月** | 跨部门、要管理后台/SSO | **~81%** |
| **Enterprise 私有化** | **¥800–1500/座位/年 + 实施费 ¥15万–50万起** | 政企/金融/信创 | 看交付人力,通常 60–70% |

> **¥39 锚点逻辑:** 低于飞书企业版一个普通席位(人均 ¥100+),客户心理账户是"加购个 AI 同事"而非"换系统"。**坚决不按 token 计费给客户**——成本已极低、per-seat 毛利已厚,"给小王配个 AI 同事 ¥39/月"比"你这月用了 230 万 token"好卖一百倍。

### 7.3 两条交付线

- **SaaS 公有云(主战场跑量):** 你统一持有 DeepSeek/GLM 合规 key,做模型聚合层赚批发零售价差 + 缓存红利。扫码当天可用,租户隔离过等保。
- **私有化(吃政企大单):** 客户**自带 key 或本地模型**(底座现成支持),**模型成本转移给客户**,你卖 license + 实施 + 运维。500 人客户 ≈ ¥50万/年 license + ¥30万首年实施。**别做太碎定制**——标准化成可重复交付包,定制单独报价,否则交付人力吃光毛利(政企 Agent 公司的死法)。

### 7.4 冷启动:Land in one team, expand by envy

切"痛感最强 + 重复劳动最多"的部门(HR/运营/行政助理,**别从工程部切**——工程师自己写脚本、付费意愿低、爱挑刺)→ Free Pilot 60 天给整部门 + 预置岗位模板 → agent 在飞书群里发周报、@催办、丢纪要,**别的部门看到"他们有个 AI 同事在群里干活"会主动来问**(飞书 IM 形态天然适合病毒扩散)→ 部门负责人转化为内部冠军,拿"省时报告"向上要预算铺全公司。

**话术主轴:** "Aily 是给公司配的 AI 部门,我们是给每个人配的 AI 同事。" 不抢"企业级 Agent 平台"这个被 Aily 占住的词,占"个人数字同事"这个空位。

## 8. 风险与红线

### 8.1 产品/技术红线

| 风险 | 应对 |
|---|---|
| **扫码建应用走私有协议,飞书随时可下线**(护城河①命门) | **必须并行做"档 3 手动 app_id/secret"优雅降级**(模板应用 + 一键导权限),监控该端点健康度。命脉不押单点。 |

| "开箱即用"被 IT 建应用门槛拆穿 | 话术分层:**员工**开箱即用 / **IT** 一次性接入 |

### 8.2 必输场景(看见就避开,别送人头)

| 场景 | 应对 |
|---|---|
| 钉钉/企微生态客户 | 直接放弃,销售不跟进 |

- Embedding 用国产合规模型(BGE/GLM),不出境。
