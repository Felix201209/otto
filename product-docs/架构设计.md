> 本机 CLI 后端 + 飞书 · 基于开源 easycode（Apache-2.0，源自 Google Gemini CLI）二次开发的独立产品
>
> 全部 file:line 已对照真实源码核验。所有路径为绝对路径。本文档面向工程实现，区分「已完成」与「待做」两个状态层。

## 0. 一句话定位

**Otto** 是围绕飞书帮企业大幅提效的 AI 数字同事产品。形态是**本机 CLI 后端（跑在用户电脑上，像 easycode）+ 飞书**——不是云端多租户 SaaS。目标：让每个员工有一个住在飞书、懂他、替他干活的 AI 数字同事。

CLI 子产品 **Otto Code**（对标 Easy Code）是这套后端的命令行入口；家族还有 Otto Desk / Otto Work / Otto Studio。

技术上，Otto 在 easycode 现有 CLI/agent 骨架（`packages/core` + `packages/cli`）之上做**增量嫁接**而非重写：

- 模型层加 **Codex OAuth / API Key 双鉴权**（已完成、已实测）。
- agent loop 借鉴 **Hermes harness** 的三样东西——记忆 Provider 抽象 + 生命周期钩子 + 单外部 Provider 约束——经现有 `turn.ts` 的 BeforeModel/AfterModel 钩子接入。
- 飞书侧**直接复用已存在的 `FeishuGateway`**。
- 明确**不做 Claude OAuth**。

easycode 不是空白底座：飞书网关（`gateway.ts`，3429 行）、CardKit 流式卡片、隔离会话、Turn 钩子、多 provider 适配器、token 管理**都已存在**。Otto 的工作是在这些现成切口上接线。

## 2. Harness：Hermes 接入点（turn.ts 钩子）

### 2.1 借鉴清单（明确取舍）

| Hermes 机制 | 借 / 不借 | 理由 |
|---|---|---|
| MemoryProvider ABC + 生命周期钩子 | **借（精简到 5 钩子）** | 干净的扩展点，端口成 TS 成本低 |
| 单外部 Provider 约束 | **借** | 防工具 schema 膨胀，一行 guard |
| `<memory-context>` fence + 上下文擦除 | **借（简化版）** | 防注入污染 LLM 输出，必要 |
| 后台 ThreadPoolExecutor + jitter retry | **不借** | Node 用 `void promise.catch()` 异步即可，无需线程池 |
| 独立 gateway 进程 + 线程池委派 | **不借** | easycode 已有 onMessage 异步回调 |
| SQLite SessionDB + FTS5/trigram 搜索 | **P2 可选** | MVP 用文件足够；检索需求出现再上 |
| 插件 register(ctx) + 18 钩子 | **P2 借子集** | easycode 已有 hooks 子系统，先复用现有 |

### 2.2 现有钩子点（嫁接锚点，已核验）

`Turn.run()` 已经内置 **Hermes 风格的钩子触发**，这是最关键的现成切口，Hermes harness 直接经此接入：

- **`turn.ts:247`** `async *run(...)` — agent 单轮主循环（生成器）。
- **`turn.ts:252-266`** `BeforeModel` 钩子 `fireBeforeModelEvent(...)` —— **记忆 prefetch 注入点**。把 `MemoryManager.prefetch()` 拿到的 `<memory-context>` 拼进即将发给模型的请求。
- **`turn.ts:280`** `BeforeToolSelection` 钩子 —— 工具过滤点（P2 用）。
- **`turn.ts:285`** `this.chat.sendMessageStream(...)` —— 实际调模型，下游进 `customModelAdapter`。
- **`turn.ts:491-501`** `AfterModel` 钩子 `fireAfterModelEvent(...)` —— **记忆 syncTurn 写回点**。
- **`turn.ts:226`** `private config: any` —— 钩子通过 config 拿全局引用；`MemoryManager` 挂在 config 上即可被钩子访问。

> 关键事实：**不需要新造钩子框架**。Hermes 的 `pre_llm_call`/`post_llm_call` 在 easycode 里已对应 `BeforeModel`/`AfterModel`。Hermes 接入 = 在这两个已存在的钩子回调里调 MemoryManager。

### 4.4 customModelAdapter 接入切口（精确）

provider 分发在 **`customModelAdapter.ts:3087-3089`**（`callCustomModel`）和 **`:3063-3065`**（`callCustomModelStream`）：

```ts
if (modelConfig.provider === 'openai') return callOpenAICompatibleModel(...);
else if (modelConfig.provider === 'openai-responses') return callOpenAIResponsesModel(...);
```

鉴权头当前在各 call 函数里硬拼 `'Authorization': Bearer ${apiKey}`（`:974`/`:1315`/`:1397`），`apiKey` 来自 `resolveEnvVar(modelConfig.apiKey)`（`:947`/`:1277`/`:1368`）。

**接入方案（最小 diff，不新增 provider 分支，复用 OpenAI/Responses 协议）**：

- Codex 走 OpenAI 兼容 / Responses 协议，**协议层不变**，只换鉴权头来源。
- 在 `callOpenAICompatibleModel`/`callOpenAIResponsesModel` 里，把 apiKey 解析改为：若 `modelConfig.apiKey === '${CODEX_OAUTH}'`（哨兵值），则 `headers = await codexAuthManager.getAuthHeaders()`，否则走现状 `Bearer ${resolveEnvVar(...)}`。
- 切口就在 `:974`/`:1315`/`:1397` 的 headers 构造前插一个分支。**不碰协议、不碰流式解析**。

> 取舍：**不新增 `codex-oauth` provider 类型**。Codex 就是 OpenAI 协议，新增 provider = 复制两套 call 函数 = 重复约 600 行。用「哨兵 apiKey + 鉴权头注入」更省。
>
> **明确不做 Claude OAuth**：`anthropic` provider（`:1594`）保持只用 `x-api-key`/`Bearer` + 静态 key，不接任何 OAuth 刷新逻辑。

### 4.5 多模型配置（已完成）

`custom-models.json` 支持多条模型（Codex / DeepSeek / OpenAI），`/model` 命令可在运行时切换。Codex 条目用哨兵 apiKey 即接双鉴权，DeepSeek/OpenAI 条目走静态 key。

### 4.6 优先级 / 生命周期

- **provider 内优先级**：`auth_mode === 'apikey'` 且 `OPENAI_API_KEY` 存在 → 用 API Key（无刷新，最简）；否则用 OAuth。
- **飞书 + Codex 嵌套 token**：两条独立生命周期，互不耦合。飞书 token 由 `FeishuGateway` 自己的 tenant_access_token 管；Codex token 由 `CodexAuthManager` 管。onMessage 回调里只在真正调模型时才触发 Codex 刷新，单飞保证一个 chatId 风暴不会引发多次刷新。

### 4.7 实测结论

- ✅ OAuth 模式实跑 `callCustomModel` 拿到 **HTTP 200 + 文本流**。
- ✅ API Key 模式实跑通过。
- ⏳ token 自动刷新：代码已按实测参数（OAuth 端点 / client_id / 单飞）写好，但**未到期触发验证**——属待验项，access_token 真实过期后需复测刷新链路。
- token 链路健壮性已加固：`getTenantToken` 单飞锁 + `res.ok` 校验 + 脱敏日志；令牌交换全程脱敏。
