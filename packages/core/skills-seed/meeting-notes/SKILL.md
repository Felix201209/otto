# 会议纪要整理

把一场会的原始记录，变成第二天所有人都能照着执行的纪要。

## 开工顺序
1. 如果用户给的是录音、视频、音频路径或会议文件，先调用 `audio_reader` 自动转写，不要先追问主题、时间、参会人，也不要因为文件较大就放弃。转写后再从内容里提取主题、时间、参会人、主持人和议题。
2. 如果 `audio_reader` 返回 setup needed，直接说明 Otto 已完成能力检查：当前模型是否支持音频、本地转写是否可用、缺少哪一项。不要要求用户手动安装 Python 转写包，也不要让用户自己找转写稿；应引导用户使用 Otto 的本地转写修复/依赖检查入口，或提示上传已有转写文本作为临时替代。
3. 如果用户给的是文字速记、聊天记录或要点，直接整理纪要；缺失的主题、时间、参会人、主持人只标为“待确认”，不要一开始连续追问。
4. 只有在纪要用途会明显影响格式时，才用 `ask_user_question` 给 2-3 个可点击选项，例如“管理层摘要 / 客户跟进 / 内部行动清单”。不要让用户打一大段需求。

## 输出结构
### 一、会议信息
主题 · 时间 · 参会人 · 主持

### 二、关键结论（decisions）
逐条列出"拍板了什么"，一句一条，不含讨论过程。

### 三、待办事项（action items）
表格：事项 | 负责人 | 截止时间 | 优先级
（没明确负责人/时间的，标注"待确认"，绝不臆造。）

### 四、讨论要点
按议题分组，保留有价值的分歧与理由，剔除寒暄与跑题。

### 五、风险 / 遗留问题
未决事项、依赖、下次会议要跟进的点。

## 纪律
- 只记"发生了什么"，不添加没说过的观点
- 分清"结论"与"讨论"——结论是已定，讨论是过程
- 负责人和时间是纪要的命脉，缺失就显式标注"待确认"，不猜
