# Otto MLS protocol design

Status: protocol draft and implementation plan. The Rust prototype validates
OpenMLS interoperability only; `device-envelope-v1` remains the active
experimental implementation until migration and release gates pass.

## Current implementation boundary

The implemented `e2ee-device-certificate-request:v2` binds `deploymentId`,
`organizationId`, `accountId`, `deviceId`, `certificateSerial`, device name,
the Ed25519 signing key, the X25519 exchange key, and an optional predecessor
certificate hash. The target device signs that request as proof of possession.
An approved device then signs the request hash, approver certificate hash,
approval time, and expiry. These exact structures are the deployed trust-v2
format and are covered by TypeScript tests.

The MLS credential described below is the next reviewed protocol format. It
adds MLS KeyPackage references and capability binding; it must receive a new
format identifier and cannot silently reinterpret a trust-v2 certificate.
Likewise, the current Merkle implementation provides inclusion proofs plus
client-side append-only pinning, but no independent witness. Cross-server MLS
delivery is a design only. The release manifest deliberately reports all three
items as incomplete.

## Standards and implementation

- Protocol: Messaging Layer Security, RFC 9420.
- Library prototype: OpenMLS 0.8.1 with the RustCrypto provider.
- Mandatory ciphersuite:
  `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- Encoding: TLS serialization produced and parsed by OpenMLS.
- Conversation model: one MLS group per one-to-one conversation. Every
  approved desktop device is a separate leaf.

No custom ratchet, HPKE construction, transcript hash, or epoch transition is
implemented outside OpenMLS.

## Identifiers

Stable protocol identifiers are opaque random bytes, not names:

- `conversationId`: 128-bit random identifier owned by the participants;
- `groupId`: `SHA-256("otto:mls-group:v1" || tenantId || conversationId)`;
- `deviceId`: 128-bit random identifier generated by the device;
- `certificateSerial`: 128-bit random identifier;
- `messageId`, `attachmentId`, and `grantId`: independent 128-bit identifiers.

All canonical application structures use deterministic CBOR. Display names,
department names, filenames, and other mutable labels are never identities.

## Device certificate

An Otto device certificate binds an account to an MLS credential and contains:

```text
version, deploymentId, tenantId, accountId, deviceId, certificateSerial,
credentialPublicKey, keyPackageReferences, issuedAt, expiresAt,
capabilities, predecessorCertificateHash
```

The target device first signs a proof-of-possession statement. An already
trusted device verifies the safety number or QR code and signs the complete
certificate request. The server verifies both signatures and authorization but
cannot create either one. Approval is append-only in the transparency tree.

The first device is a visible TOFU bootstrap until its certificate checkpoint
is witnessed. Recovery creates a new device certificate; it never reactivates
or copies the lost device identity.

## Key packages and group creation

Each approved device maintains a bounded pool of single-use OpenMLS
KeyPackages. The server may distribute public KeyPackages but must atomically
mark them consumed. A creator checks the device certificate, transparency
proof, KeyPackage signature, lifetime, ciphersuite, and replay status before
adding it.

For a one-to-one conversation, the initiating device creates the group and
adds all currently approved devices for both accounts. Welcome and Commit
messages are stored as opaque delivery records. Devices acknowledge the same
epoch before the conversation is shown as fully verified.

## Messages and attachments

Message application data uses deterministic CBOR:

```text
version, messageId, conversationId, contentType, body, attachmentManifests,
inReplyToMessageId, createdAt, senderAccountId, senderDeviceId
```

The complete structure is passed to OpenMLS `create_message`. The server
receives only MLS ciphertext and routing metadata.

Large attachment bytes are encrypted separately. For each attachment, the
sender derives a 256-bit key from the current MLS epoch exporter using label
`otto:attachment:v1` and context containing tenant, conversation, epoch,
message, attachment, size, and MIME digest. XChaCha20-Poly1305 or AES-256-GCM
uses a fresh nonce. The encrypted attachment manifest is part of the MLS
application message, preventing object substitution.

Changing membership commits a new epoch before any subsequent application
message. Removed devices receive no exporter secret for the new epoch.

## Local search

After successful MLS authentication, the desktop indexes normalized message
text and attachment display names into a per-account SQLCipher database. Its
key is derived independently from local secure storage, not an MLS epoch key.
The index stores conversation and message references plus encrypted snippets;
it is never synchronized to the enterprise server.

Search results are accepted only if the referenced message still exists and
decrypts under the current pinned device/transparency state. Logout, account
deletion, or server-scope changes close and wipe the corresponding index.

## One-time A2A authorization bridge

Private chat is not an implicit Agent data source. A local device may issue a
signed grant containing:

```text
grantId, tenantId, requesterAccountId, responderAccountId, requesterDeviceId,
purpose, selectedMessageDigests, allowedSources, maxBytes, issuedAt, expiresAt,
nonce, targetAgentId, requestMessageId
```

The local A2A bridge verifies the device certificate and signature, checks the
request identity, consumes the nonce in a local encrypted replay store, loads
only content matching the committed digests, and destroys the assembled
plaintext after one invocation. The grant cannot be delegated, refreshed, or
used on another device. The response returns as an MLS application message.

## Transparency

The server maintains an append-only Merkle tree over canonical device
certificate events and publishes:

- tree size and root hash;
- inclusion proof for every returned certificate event;
- consistency proof from the client's pinned tree size;
- a signed checkpoint from an independent Otto witness;
- optional participant gossip checkpoints inside MLS messages.

Clients reject invalid inclusion or consistency proofs, decreasing tree sizes,
two roots for one witnessed tree size, expired witness signatures, and device
directories that do not exactly match active certificate events.

The existing linear SHA-256 chain is migration input, not the final Merkle
transparency protocol.

## Cross-server delivery

Each private server has a signed deployment identity issued by Otto Control.
Servers and the gateway use mutually authenticated TLS. A federation envelope
binds source deployment, destination deployment, tenant/account routing,
message identifier, expiry, nonce, payload digest, and protocol version. The
gateway verifies routing signatures, replay state, quotas, and revocation, but
stores and forwards only opaque MLS records.

Identity discovery and transparency proofs must be globally consistent before
cross-server group creation. A server or gateway cannot add itself as an MLS
member.

## Recovery and migration

Recovery bundles contain user-held recovery material encrypted with a
memory-hard KDF and AEAD. Import creates a new device, performs explicit
proof-of-possession, and requires recovery authorization recorded in the
transparency tree. Administrators cannot bypass this ceremony.

Legacy `device-envelope-v1` history is never decrypted or re-encrypted by the
server. A participant-side migration tool may decrypt legacy history locally,
re-encrypt it into a clearly marked MLS archive, and preserve provenance. New
messages cannot silently downgrade to the legacy protocol or plaintext.

## Release gate

Production activation requires all of the following:

1. protocol and storage migrations pass desktop/server interoperability tests;
2. malicious-server, database-tamper, device-loss, replay, fork, and federation
   tests pass on every supported platform;
3. a third-party audit artifact identifies the exact source commit and protocol
   version and all critical/high findings are closed;
4. Otto signs a release approval containing that audit digest;
5. the deployment has a signed module policy enabling the reviewed MLS module.

Missing or invalid evidence keeps the feature disabled. It must not trigger a
plaintext fallback.
